IC optimization workflow / local + remote

IC Auto Opt Workflow 架构地图

这页给维护者用。先看入口怎么分发，再看 requirement 怎么变成配置合同， 真实 Spectre/OCEAN 在哪里跑，结果最后写到哪些 manifest、report 和 state 文件。

optimize 候选点搜索循环。后端提出 batch，执行 Spectre/OCEAN，读取 metric，再更新模型。
fix_run 不搜索。按固定点跑真实仿真，保存 scalar metrics 与 waveform CSV。
source of truth 先看 `opt_requirement.md`，再看 `config/*.yaml` 和落盘 artifacts。
维护压力 大编排函数、OpenBox batch loop、测试模板耦合最容易带来漂移。

外层产品流程

外层流程先收紧输入，再检查环境和项目状态，最后才交给 optimizer 或 fix-run。 任何一步失败，都应该停在对应的 report 里，而不是继续跑真实工具。

src/hermes_workflow/optimizer_flow.py

外层管合同

它把用户输入变成可复现项目，不在这里写优化算法。

backend 管循环

candidate 选择、真实执行和模型更新都在 backend 里发生。

report 管验收

CLI 输出只方便人看。事实要回到 `reports/`、`runs/real/` 和 `state/`。

Optimizer 内层循环

Markdown 顶层图容易把这里压成一个 backend 节点。实际运行时，optimizer 会反复建议候选点、 跑真实仿真、记录 observation，再更新模型，直到预算或停止条件结束。

OpenBox / native TuRBO

不是线性单次执行

外层 workflow 调一次 backend，backend 内部按 batch 循环跑真实仿真。

并行粒度

optimizer 模式的 `parallel_jobs` 主要是 candidate-level 并行。

最挤的函数

`_run_openbox_batches()` 同时处理 planning、execution、observation 和 report。

Fix-run 固定点执行

fix-run 跑用户给定的参数点。它复用 real-run package、Spectre/OCEAN adapter 和结果校验，但不搜索新参数，也不更新 optimizer state。

src/hermes_workflow/fix_run_flow.py

并行边界

`parallel_jobs` 管 child 并发。`threads_per_run` 管单个 Spectre 进程。

结果边界

fix-run 不写 optimizer state，也不选 best candidate。

验收重点

scalar、waveform CSV、manifest 和失败原因都要落盘。

Remote 是传输层，不是第二套业务

remote optimizer 通过 service injection 复用 local optimize。remote fix-run 也沿用同一套报告格式， 只是多了 SSH、cache 和 artifact sync。

remote_project / remote_runner
RemoteProjectRef

remote 身份对象，绑定 ssh profile、remote project dir 和本地 cache。

RemoteSshRunner

执行远端命令。这里应该只管传输，不写业务判断。

remote optimizer

复用 `optimize_project()`，把 adapter 和服务替换为 remote 版本。

remote fix-run

child 调度语义对齐 local，最后同步 report 和 artifact。

Artifact 地图

这个项目的验收事实主要不在控制台输出，而在 manifest、report、ledger 和 state 文件。

reports / runs / state
config/

requirement 渲染后的结构化合同：project、variables、metrics、spectre、optimizer。

execution_package/

执行包和 immutable manifest。真实 run 前必须通过 approval gate。

runs/real/<run_id>/

候选点或固定点的真实执行目录，包含 netlist、result manifest、metric request。

reports/

用户和 agent 的主要读取入口，包括 doctor、optimizer、fix-run、decision report。

metric_result_manifest.json

scalar metric 的合同文件。缺失、非数值、hash drift 都应该 fail-closed。

waveform_export_manifest.json

waveform CSV 的索引合同。fix-run 重点确保 CSV 确定落盘。

ledger/

真实评估记录，连接 candidate、metric、状态和后续总结。

state/

optimizer 状态、health、继续运行需要的上下文。

源码阅读路线

先看用户入口和合同层，再看 optimize/fix-run 编排，最后进入 backend、adapter 和 remote。

recommended path

  • src/hermes_workflow/requirement_intake.py 把 `opt_requirement.md` 转成可执行配置。
  • src/hermes_workflow/validate.py `assert_valid_project()` 和 `ContractBundle` 的入口。
  • src/hermes_workflow/optimizer_flow.py optimize 产品门禁顺序。
  • src/hermes_workflow/fix_run_flow.py 固定点、child 调度、waveform artifact。
  • src/hermes_workflow/openbox_backend.py OpenBox batch loop 和 observation 更新。
  • src/hermes_workflow/real_run.py 真实 run package 和 candidate 渲染。
  • src/hermes_workflow/execution_adapters/spectre_ocean.py Spectre/OCEAN adapter 和 metric/waveform 输出。

复杂度热区

当前项目已经有清楚的合同层和执行层。风险在大函数继续变大，最后让一个局部修复牵动全局语义。

governance map
区域 判断 建议处理
product_cli.main() 用户入口可读，但分发逻辑偏大。 按 local/remote、doctor/continue、real/fix-run 拆 handler。
optimize_project() 门禁顺序显式，函数长度已经形成维护压力。 先加测试，再拆 plan builder 和 step executor。
_run_openbox_batches() 复杂度最高，混合 batch planning、execution、report 和 early stop。 拆 candidate planning、evaluation、observation、audit/report persistence。
create_project_from_template() 这是产品 API，不适合作为通用测试 fixture。 继续推进 generic test factory，缩小 allowlist。
